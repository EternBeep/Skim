01 · The Big Picture

What Week 3 actually changed

Week 2 was a working demo that ran only on your laptop. Week 3 is a plumbing upgrade: the intelligence stayed identical (CLIP + Whisper + librosa + Reciprocal Rank Fusion), but storage, media, and state all moved to the cloud — so it caches globally, survives restarts, and won't crash under concurrent users.

The one-sentence summary

Replace every local file (ChromaDB on disk, JPEGs on disk, an in-memory registry) with a cloud service (Pinecone, Cloudinary, Redis), add a global cache so repeated URLs are instant for everyone, and a single worker so simultaneous indexing can't take the server down.

02 · System Architecture

How the pieces fit together

Three independent cloud services hang off one backend. The frontend (Vercel) only ever talks to the backend (HF Spaces); the backend talks to Pinecone, Cloudinary and Redis.

stores

Pinecone holds the math: 512-dim vectors for every frame & spoken line, searched by cosine similarity.

serves

Cloudinary hosts the JPEG thumbnails on a global CDN, so images load fast and the server stays stateless.

remembers

Redis is the shared memory: "who's indexed what" + live job status, readable by anyone.

⚠ Two honest deviations from the original plan

R2 → Cloudinary. Cloudflare R2 requires a credit card to activate — which breaks goal #7. Cloudinary gives 25 GB free with no card and a built-in image CDN, so it's a strictly better fit for thumbnails.

Render → Hugging Face Spaces. Render's free tier is 512 MB RAM — torch + CLIP + Whisper would get OOM-killed. HF Spaces gives 16 GB RAM, no card, and actually fits the model stack.

Redis BLPOP → in-process queue. Upstash's free tier drops long-idle blocking connections, so a persistent BLPOP worker got stuck. Since HF runs a single instance, an in-process queue serializes jobs just as well — and Redis still stores job state + the global cache.

06 · Data Flow — Search

"Seen + Said" search, fused

Your query is encoded into two spaces at once, each space is searched separately in Pinecone, and the two ranked lists are blended with Reciprocal Rank Fusion (RRF) — so a moment that's both shown and spoken rises to the top.

Why two spaces?

CLIP understands images + short visual phrases. MiniLM understands spoken language. A query like "someone says thank you" is a spoken match; "slow dramatic reveal" is a visual one. Searching both and merging is the whole trick.

Why RRF (not score-mixing)?

The two cosine scores live on different scales, so you can't just add them. RRF only cares about rank position (1st, 2nd, 3rd…), so the lists combine fairly. Moments hitting in both lists get tagged "Seen + Said".

🧠 The clever bit: one index, two vector sizes

Pinecone indexes are fixed-width. CLIP is 512-dim, MiniLM is 384-dim. The fix: zero-pad MiniLM up to 512. Because every search filters by source, a padded vector is only ever compared to other padded vectors — the trailing zeros cancel in both the dot-product and the norms, so cosine scores are mathematically identical to native 384-dim. Two embedding spaces, one free-tier index.
